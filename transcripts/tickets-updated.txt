## 1. Model fusion — fuse all, weighted                                         
                                                                                
All experts always contribute. Meta-learner learns context-conditioned weights; 
no hard pick.                                                                   
                                                                                
fused_logodds = Σ_i w_i(u_t) · logit(expert_i)                                  
experts = { hazard, forecast, graph, vae }                                      
w_i = softmax gate over context vector u_t   # can spike toward one expert, but 
never zeroes the rest                                                           
                                                                                
Robustness reason: a single mis-firing expert gets down-weighted, not handed    
the whole call.                                                                 
`expert_weights` stays in the output for interpretability (e.g. `hazard .51 /   
forecast .22 /                                                                  
graph .15 / vae .12`).                                                          
                                                                                
## 2. Hazard model — standalone head                                            
                                                                                
A dedicated head emits **one softmax over `K·J + 1` logits** = joint PMF over   
(fault-type `k`,                                                                
time-bin `j`) plus a "no impact in horizon" mass. Everything below is a         
deterministic readout of                                                        
that one distribution, so the sub-outputs cannot contradict each other:         
                                                                                
| Quantity | Formula |                                                          
|---|---|                                                                       
| Cumulative incidence `F_k(h)` | `Σ_{j≤h} p_{k,j}` |                           
| Survival `S(h)` | `1 − Σ_k F_k(h)` |                                          
| Discrete hazard `λ_k(j)` | `p_{k,j} / S(j−1)` |                               
| Time-to-impact | `argmin_h {F_k(h) ≥ 0.5·F_k(J)}` + IQR from `F_k` |          
                                                                                
Fault types: multi-label, 2-level hierarchical (coarse family → fine type), so  
concurrent faults                                                               
are native. 21 labeled fault types from the simulator.                          
                                                                                
## 3. LLM copilot — agentic investigator                                        
                                                                                
The copilot is a **tool-using agent**, not a summarizer. Loop:                  
                                                                                
think → pick tool → run it → read result → decide next → ... → cited answer     
tools = { search_logs, query_metrics, walk_topology_graph, search_runbooks,     
search_incidents }                                                              
                                                                                
- Harness = little-coder pattern, adapted for the smaller **gemma** model.      
- **ReGain** framework provides the RAG layer (forensic retrieval over          
incident/runbook corpus).                                                       
- Runs **sandboxed**: read-only data access, no network, resource-limited —     
can't do anything                                                               
  destructive or leak data.                                                     
- The agent decides step-by-step what to look up next based on what it has      
already found — same as                                                         
  how an engineer works a ticket. Not top-k-once RAG.                           
                                                                                
Doc A's separate `/explain` endpoint is **gone** — explanation is now what the  
agent produces, on                                                              
demand, inside whichever mode is active (see §6).                               
                                                                                
## 4. Trust — both layers                                                       
                                                                                
Two independent gates guarding two different things:                            
                                                                                
- **Statistical (on the model numbers)** — conformal risk control (guaranteed   
FPR bound),                                                                     
  context-conditioned temperature calibration,                                  
aleatoric/epistemic/gate-variance split reported                                
  separately, and an **abstain** flag when there's no confident call.           
- **Evidential (on the agent's answer)** — every pulled piece of evidence       
carries provenance (which                                                       
  log, which time range, which graph node). Before the agent may answer, a      
**quality gate** checks:                                                        
  did tool calls succeed, is evidence relevant to the question + time window,   
is it sufficient, do                                                            
  sources agree. Fail → the system says *what's missing* instead of forcing an  
answer. Pass → every                                                            
  claim in the final answer traces to a specific evidence item (citations).     
                                                                                
## 5. Graph — two graphs, one topology                                          
                                                                                
Same network topology feeds two distinct consumers. Do not conflate them.       
                                                                                
- **STGNN (neural predictor)** — topology → spatio-temporal embeddings → feeds  
the hazard head.                                                                
  Reasons about cascading failure. Localization via attention attribution,      
GNNExplainer minimal                                                            
  subgraph, and counterfactual edge-removal ("remove this link, does risk drop  
→ recommended                                                                   
  action").                                                                     
- **Knowledge graph (symbolic, walkable)** — devices/links/VRFs as nodes;       
**past incidents and                                                            
  runbooks attached as nodes** linked to the specific device/link-type they     
apply to. The agent                                                             
  walks it outward for **blast-radius** ("if this link fails, what's            
downstream") and                                                                
  proximity-based history lookup (not keyword search).                          
                                                                                
Shared topology source, two representations.                                    
                                                                                
---                                                                             
                                                                                
## 6. Analysis modes — Live vs Forensic                                         
                                                                                
The split is by **time-of-interest**, not latency. Doc A's sync/async endpoint  
split is dropped;                                                               
the agent's explanation lives inside the mode.                                  
                                                                                
### Live mode                                                                   
- Model runs **continuously**, predicting off the **last X minutes relative to  
the live point**                                                                
  (rolling window).                                                             
- The **same last-X-minutes window is the LLM's context** for                   
answering/explaining questions about                                            
  a current or developing failure.                                              
- Context is a **sliding window**: as time advances, data older than X minutes  
**drops out of                                                                  
  context**. The agent always reasons over "recent relative to now."            
- Use: "what's happening right now / about to happen," live monitoring,         
comparing current state.                                                        
                                                                                
### Forensic mode                                                               
- Takes a **snapshot** at a chosen point (e.g. auto-triggered when the PA       
system fires a fault),                                                          
  and predicts off that snapshot.                                               
- **Saves the last X minutes relative to the snapshot time** as a frozen        
window.                                                                         
- The agent answers **only from that frozen window** — **no new/live data leaks 
in**. Reasoning                                                                 
  stays reproducible for the postmortem.                                        
- Use: postmortems, root-cause after the fact, "what was the exact state when X 
broke."                                                                         
                                                                                
X = configurable (default ~10 min; tune to fault cascade timescale)             
ponytail: single X for both modes to start; split into live_X / forensic_X only 
if one window proves wrong                                                      
                                                                                
                                                                                
| | Live | Forensic |                                                           
|---|---|---|                                                                   
| Trigger | continuous | snapshot (PA fault or manual) |                        
| Window | last X min, **rolling** | last X min at snapshot, **frozen** |       
| New data | flows in, old drops out | **sealed — none enters** |               
| Purpose | monitor now | postmortem |                                          
| Reproducible | no (moves) | yes (fixed) |                                     
                                                                                
Both modes run the **same** three experts + hazard head + agent + both graphs.  
Only the data                                                                   
window and its mutability differ.

  ---
  Q1 — The open question: does Live/Forensic windowing belong to the copilot, or
  is it a shared service?

  What I found decides this cheaply. Every backend tool already takes start/end
  epoch params (/metrics, /events). So "windowing" is not a new service — it's
  just which start/end the agent passes:

  - Live = agent computes end=now, start=now−X fresh on each tool call
  (rolling).
  - Forensic = agent pins end=T_snapshot, start=T_snapshot−X once and reuses it
  (frozen). "No live data leaks in" = the agent is forbidden to pass any end > 
  T_snapshot.

  My recommendation: windowing is copilot-only — a thin WindowContext {start, 
  end, frozen} the agent threads into every tool call. NOT a shared service. The
  prediction stack does its own windowing independently (it already reads
  /datasets?start&end). The §6 line "the window wraps every expert + the agent"
  is describing a concept, not a shared component — each consumer bounds its own
  reads. This keeps the subsystem boundary clean: nothing in the copilot
  reaches into the prediction stack.

  The one thing this leaves: forensic "freeze" needs the underlying data to
  still be queryable at T_snapshot−X later (retention). VictoriaMetrics/Loki
  retention must exceed your postmortem horizon, OR forensic snapshots the rows
  to disk at capture time.

  Do you accept windowing as copilot-owned WindowContext (not a shared service),
  with forensic freeze enforced by (a) query-time param pinning + (b) a
  retention floor — snapshot-to-disk only if retention proves too short?

● Let me explain it plainly, with a concrete example.

  What the quality gate is

  The agent gathers evidence (log lines, metric values, topology facts, past
  incidents), then wants to answer. The quality gate is a checkpoint between 
  "gathered evidence" and "allowed to answer." Its job: stop the agent from
  confidently answering when its evidence is thin, off-topic, or contradictory.
  A small local model will bluff — the gate is what catches the bluff.

  Two outcomes:
  - Pass → agent writes the answer, and every claim must point to a specific
  evidence item (citation).
  - Fail → agent does not answer. Instead it says what's missing ("no BGP logs
  in this window for pe1 — can't confirm the flap").

  Why two stages

  Checking evidence quality has an easy half (pure code, instant, free) and a
  hard half (needs a language model to judge). Doing the easy half first means
  you throw out obvious garbage without wasting an LLM call.

  Stage 1 — code checks (deterministic). Plain if statements, no AI:
  - Did every tool call actually return data, or did some error out / come back
  empty?
  - Is each piece of evidence inside the time window the question is about? (A
  log line from yesterday doesn't count for "what's happening now.")
  - Does the evidence mention the devices in the question? (Asked about pe1, but
  all evidence is about ce_branch5 → mismatch.)
  - Is there enough? (At least N items; every thing the answer names has at
  least one supporting item.)

  If any of these fail, stop here — cheap, obvious, no model needed.

  Stage 2 — one LLM-judge call. Only the fuzzy questions code can't answer:
  - Is this evidence actually relevant to what was asked (not just same
  device/time, but on-topic)?
  - Does it actually answer the question, or just circle it?
  - Do the pieces agree, or does one log say "link up" while a metric says
  "down"?

  One call. Input = the question + the collected evidence. Output = a small
  structured verdict:

  { "pass": false,
    "missing": ["no metric confirming tunnel loss for ce_branch5→hub1"],
    "contradictions": [] }

  That missing list is literally what the agent tells the user on a fail. No
  separate "explain what's wrong" logic — the judge already produced it.

  Concrete walk-through

  ▎ Q: "Is tunnel ce_branch5→hub1 about to breach SLA?"

  1. Agent pulls metrics + logs + the prediction record.
  2. Stage 1: metric query returned data ✅, timestamps in window ✅, device
  matches ✅, 3 items ≥ N=2 ✅ → proceed.
  3. Stage 2 judge: "Evidence shows latency rising but no loss/jitter data —
  insufficient to call an SLA breach." → pass:false, missing:["loss/jitter for 
  the tunnel"].
  4. Agent replies: "Can't confirm — latency is climbing, but I have no loss or 
  jitter data for this tunnel in the window." — instead of guessing "yes."

  That's the whole mechanism: cheap code rejects the obvious, one judge call 
  handles the subtle, a fail becomes an honest "here's what I'd need."

  The two open decisions (plainly)

  A. Who plays judge?
  - Self-judge (v1) — the same model reviews its own evidence. Cheap, simple.
  Weakness: a model grading itself sometimes rubber-stamps.
  - Separate critic — a second, independent judgment pass. Stronger, catches
  more, but more calls/complexity.

  My rec: self-judge now, leave a note to upgrade to a separate critic if it
  proves too lenient. Don't build the harder thing until the easy thing visibly
  fails.

  B. The threshold N — how many evidence items counts as "enough." Start at 2,
  tune once you see real runs. Not worth agonizing over up front.

  ---
  So: Stage-1 code checks + Stage-2 single judge call, self-judge for v1, N=2.
  Good enough, or do you want the independent critic from day one?

● No worries. Q13 plainly:

  What "sandbox" means here

  The agent runs a language model that does things on your machine. A sandbox is
  the fence around what it's allowed to touch — so a wrong or weird model
  output can't damage anything.

  Two kinds of "touch" to fence:

  1. Reading/writing data. The agent's tools hit your metrics, logs, topology,
  incident store. The fence: those tools are read-only — the agent can look at
  everything but can't change the network or the stored data. The only place
  it's allowed to write is its own chat/case folder. This part is basically free
  — you just don't build write-tools.

  2. Running code. Earlier you said the agent may generate code or a chart to 
  diagnose an issue. There are two very different meanings of that, and which
  one you pick changes everything:

  - Emit-only — the agent writes the code/chart-spec and shows it. Something
  safe renders it (e.g. a chart library draws the spec). The model's code never
  actually executes as a program. → No sandbox needed. Much simpler.
  - Execute — the agent writes Python and the system runs it to compute a
  result. → Now you need a real fence, because you're running model-written
  code. That fence = run it in a restricted subprocess: no internet, a throwaway
  temp folder, capped CPU/memory/time, only safe libraries (pandas,
  matplotlib). Enough to stop it hanging the box or reaching out, without the
  weight of full containers.

  The two decisions

  (1) Does the agent actually execute generated code, or only emit it for 
  display?
  - Emit-only = simplest, no sandbox, but the agent can't compute novel things —
  it's limited to what the 5 tools return.
  - Execute = more powerful (it can crunch numbers, build custom analysis), but
  needs the subprocess fence.

  (2) If it executes — is a restricted subprocess enough for now, or do you want
  full container isolation from day one?
  - My rec: subprocess is enough until this is deployed somewhere adversarial;
  containers/seccomp later if the threat model demands. Don't build the heavy
  version first.

  My overall recommendation: read-only tools (always), and start emit-only — the
  agent shows charts/code but doesn't run arbitrary Python yet. Add the
  executing-sandbox only when you hit a real diagnosis the 5 tools genuinely
  can't answer. That's the laziest safe path.

  Which do you want for (1) — emit-only, or execute-with-subprocess?

  Q15 — Forensic auto-trigger: how it actually fires.

  Given #2, the pieces line up: PA (or the emulator) writes prediction records 
  into the Event Ledger (append-only). So the trigger is just a small watcher 
  tailing that stream.

  My proposed mechanism:
  - A watcher service (background loop) reads new records from the ledger.
  - A record fires a case when its decision says so — e.g. decision.alert == 
  true (PA.md §3.3 has this field).
  - On fire: allocate case_id → freeze the window at record.ts → copy the
  concerned observability period into cases/<id>/window/ → write prediction.json
  → generate the initial report (case.md) → spawn the investigation chat(s)
  (n+master if n_concurrent>1).

  The nuance that matters — don't open a case per record. A single fault episode
  emits many records over minutes (the same congestion, ticking). Naive = 50
  duplicate cases for one incident.

  My rec — one case per episode: key by scenario_id (or
  device+fault_type+time-proximity). First alerting record opens the case; later
  records for the same episode update it (append to its ledger/window), don't
  spawn new ones. Episode ends → case ready for verdict.

  Restart safety: watcher tracks the last-processed record id in the ledger; on
  restart it resumes from there, idempotent by record id — no double-fire, no
  missed alerts.

  Decisions:
  1. Trigger = watcher tailing the prediction-record stream, fires on
  decision.alert==true — yes?
  2. One case per episode (dedup by scenario_id/device+fault), updated as
  records arrive — or simpler one-per-record?
  3. Anything besides alert==true that should fire a case (e.g. abstain==true
  with high novelty — "something weird, no confident call")?

  Q16 — Context management (the make-or-break #5). Your "retrieval handles it" 
  covers the corpus, but not the real overflow source.

  Retrieval chunks the runbook/incident corpus — good, that's bounded. But the
  small model's context gets blown by three things retrieval doesn't touch:

  1. Raw tool results. /events returns up to 1000 log rows; /metrics returns
  arrays of hundreds of points; a forensic window/ copy is large. One tool call
  can exceed the model's whole context.
  2. Chat history. Long investigations + all those visible tool_call/tool_result
  events pile up.
  3. The frozen forensic window — potentially minutes of multi-device telemetry.

  Your instinct — "if the model is smart enough in how it retrieves specific 
  chunks" — is the right direction, but a weak model won't self-limit; it'll ask
  for 1000 rows and drown. So the system has to bound it, cheaply:

  My recommendation — three lazy guards, no fancy infra:
  1. Tool results are paged + summarized, never dumped. A tool returns a capped 
  preview (e.g. top 20 rows + counts/stats: "1000 events, built from 40
  ADJCHANGE bursts on pe1") + a result_id. The agent drills down on demand
  (get_page(result_id, 2) / filter) instead of receiving everything. Turns "1000
  rows" into "a summary it can act on." # ponytail: cap+paginate at the 
  adapter; the model pulls detail only when it needs it
  2. History compaction. When the event log passes a token budget, summarize 
  older turns into a running "investigation so far" note; keep recent turns
  verbatim. (Same sliding-window idea as WindowContext, applied to the chat.)
  3. The window is queried, not loaded. The forensic window/ copy is on disk;
  the agent hits it through the same paged tools, never reads the whole thing
  into context.

  Net: the model always sees summaries + handles, and fetches detail
  deliberately. That's what makes a small model survive big telemetry.

  This is a real component (result-paging in the tool adapter + a
  history-compactor) — its own ticket, and it touches every tool, so it's a
  Milestone-A blocker, not a nice-to-have.

  Decisions:
  1. Tool results = capped preview + summary + drill-down handle (not raw dumps)
  — accept?
  2. History compaction at a token budget (summarize old, keep recent) — accept,
  or keep full history and rely on a bigger context window?
  3. Who summarizes a big tool result — deterministic code (counts/stats/top-N,
  cheap, my rec) or an LLM pass (richer, costs a call)?

● Let me back up and explain plainly — no jargon.

  What "the spec" is

  We wrote ADRs = the decisions and why (17 little docs: "we chose LanceDB
  because…"). Good record, but scattered.

  A spec (some call it a PRD) is one document that describes the thing to build,
  from the user's point of view, in a fixed shape:
  - Problem — what's wrong today.
  - Solution — what we're building, plainly.
  - User stories — a long list of "As a NOC engineer, I want X, so that Y."
  - Implementation decisions — the components + their contracts (pulled from the
  ADRs).
  - Testing decisions — how we'll prove it works.
  - Out of scope / notes.

  It's the single source the tickets get cut from. ADRs = why; spec =
  what-to-build, in one place. That's the step I skipped and you caught.

  What "seams" are (the part you're asking about)

  A seam = a place you can cut into the system to test it — a boundary where you
  can swap the real thing for a fake one, so a test runs fast and predictably.

  Why it matters: the copilot talks to two things that are slow and 
  unpredictable in a test —
  1. the LLM (gives different words every run, needs a GPU/network), and
  2. the live data backend (VictoriaMetrics/Loki have to be running).

  If a test needs those for real, it's flaky and slow. So we put a seam at each:
  in a test, replace the LLM with "return exactly these scripted words" and
  replace the data backend with "return exactly these canned log rows." Now the
  test is deterministic.

  The skill asks me to pick the fewest, highest seams — because every seam is a
  spot the code has to be structured to allow swapping, and too many makes the
  code messy. Fewer = cleaner.

  What I proposed, in plain words

  - Test the behavior at the top — send a real chat request to the copilot's web
  API, check the answer + the steps it showed. That's the "does it actually
  work" test. (one behavior seam)
  - To make that test predictable, fake two things underneath: the LLM (scripted
  replies) and the data adapter (canned telemetry). Both are already single,
  isolated pieces by our ADR design, so faking them is easy — we don't have to
  cut new holes.
  - (Milestone B adds one more fake: the thing that runs code, so tests don't
  actually spawn programs.)

  So: 1 place we test real behavior + 2 places we swap in fakes to keep it fast.
  That's it — the skill just wants me to confirm those are the right spots
  before I write the spec, because they shape how the tickets get built and
  tested.

  Do those two fakes (LLM + data adapter) sound right to you? If yes, I write
  the spec doc and post it. If "just build it, I trust the seams," say so and
  I'll proceed.
